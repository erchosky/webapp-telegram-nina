# Auditoría técnica — 2026-07

## Alcance y resultado

Se revisaron rutas API, Server Actions, middleware, autenticación Telegram y
admin, cliente Supabase de servicio, migraciones SQL, RLS, configuraciones,
dependencias y pruebas. No se usó una base Supabase ni un bot reales: las
conclusiones sobre RLS y Telegram son revisión estática y pruebas con mocks,
no una validación en staging.

## Correcciones aplicadas

- **Media — cuerpo ilimitado en el webhook de Telegram.** Antes de analizar
  JSON, el webhook podía asignar cuerpos arbitrariamente grandes. Ahora
  `lib/telegram/webhook-payload.ts` rechaza tanto `Content-Length` excesivo
  como cuerpos reales de más de 1 MiB, sin registrar el contenido.
- **Baja — contrato público de intereses no validado.** `POST
  /api/marketplace/interest` trataba JSON sin validar como si tuviera las
  propiedades esperadas; valores como `null`, identificadores inválidos o
  mensajes gigantes podían acabar en errores 500. El contrato Zod exige UUID,
  mensaje opcional normalizado de hasta 1.000 caracteres y no admite claves
  extra. La validación también se mantiene en la capa de servicio.
- Se añadió cobertura V8 reproducible con `npm run test:coverage` y se ejecuta
  en CI.

## Controles verificados estáticamente

- Todas las tablas creadas por las migraciones activan RLS, revocan
  `anon/authenticated` y conceden acceso solamente a `service_role`; las
  funciones RPC también revocan ejecución pública.
- Las rutas de usuario pasan por validación criptográfica de `initData` de
  Telegram; administración requiere sesión firmada y sesión revocable en DB;
  webhook y cron comparan secretos en tiempo constante.
- Las mutaciones administrativas aplican comprobación de origen, sesión,
  limitación y validación de formularios. Los recursos de usuario se consultan
  con el identificador derivado de `initData`, no desde IDs proporcionados por
  cliente.
- CSP, HSTS en producción, cookies `httpOnly`/`sameSite=lax`, cabeceras de
  seguridad y respuestas privadas sin caché están configuradas.
- No se localizaron secretos reales en el código ni en el ZIP limpio; las
  variables `NEXT_PUBLIC_*` usadas son branding, flags y contacto público.

## Cobertura y verificación

La última ejecución cubrió 273 pruebas en 61 archivos. Cobertura global:

| Statements | Branches | Functions | Lines |
| --- | --- | --- | --- |
| 67,72 % | 58,43 % | 70,09 % | 72,79 % |

Los módulos de autenticación/validación más sensibles tienen pruebas directas
para tokens de sesión, revocación, `initData`, firma de webhook, deduplicación,
rate limiting y cuerpos malformados. No se alcanzó el objetivo global del 80 %:
gran parte del dashboard, integración de bot y servicios de base de datos no
pueden ejercitarse sin un entorno Supabase/Telegram de integración. No se han
excluido esos módulos artificialmente del informe.

Se ejecutaron con éxito `npm ci`, `npm run lint`, `npm run typecheck`,
`npm test`, `npm run test:coverage`, `npm run build`, `npm audit
--audit-level=high`, `npm run zip:clean` y `npm run zip:verify`. `npm run
check:env` se ejecutó y reportó la ausencia esperada de `.env.local`.

## Riesgo residual y siguiente paso

Antes de producción hay que aplicar las migraciones en una base vacía y hacer
el checklist de staging con un bot/grupo de prueba. Añadir pruebas de
integración contra Supabase y Telegram es la vía adecuada para elevar cobertura
en autorización, RLS, cron y operaciones administrativas sin convertir los
tests unitarios en mocks artificiales.
